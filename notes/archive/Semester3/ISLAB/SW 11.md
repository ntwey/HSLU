# Laborübung: Docker Security

## 1. Vorbereitung & Grundlagen
* **Ziel der Übung:** Praktischer Umgang mit Docker-Containern unter dem Aspekt der IT-Sicherheit. Verifikation der Theorie mit praktischen Angriffs- und Schutzszenarien.
* **Kern-Technologien zur Isolation:** * **Control Groups (cgroups):** Zuweisung und Limitierung von Systemressourcen (CPU, RAM) an Prozesse. Sie isolieren die Ressourcen-Subbäume voneinander.
  * **Namespaces:** Sorgen für die logische Trennung (z. B. User Namespaces zur Abstraktion des Root-Benutzers).
* **Umgebung:** Debian 12 (bookworm) Linux-Client mit einer vorbereiteten Docker-Umgebung.

---

## 2. Docker Benchmark (Auditing)
* **Konzept:** Docker bietet standardmäßig einige Sicherheitsvorgaben, diese reichen für produktive Umgebungen jedoch oft nicht aus.
* **Tool:** **Docker Security Bench** ist ein automatisiertes Skript, das die Docker-Konfiguration anhand von CIS-Best-Practices prüft.
* **Klassifizierungen des Benchmarks:**
  * `PASS`: Kriterium erfüllt.
  * `WARN`: Nicht erfüllt – akuter Handlungsbedarf.
  * `INFO` / `NOTE`: Konnte nicht geprüft werden oder sollte manuell validiert werden.
* **Prüfkategorien:** Host-Konfiguration, Daemon-Konfiguration (und dessen Dateien), Images/Build-Files, Container-Runtime, Security Operations und Swarm-Konfigurationen.

---

## 3. Hacking Docker Containers (Angriffsszenarien)
Fehlkonfigurationen im Container-Umfeld stellen erhebliche Risiken dar (z. B. Local Privilege Escalation oder Remote Code Execution).

### 3.1. Ausnutzen von Schwachstellen in Images (Shellshock)
* **Mechanismus:** Wenn verwundbare Software (wie eine alte Bash mit Shellshock) in einem Image läuft, können Angreifer über maniplierte HTTP-Header (z. B. `User-Agent`) eigenen Code einschleusen und ausführen.
* **Auswirkung:** Aufbau einer **Reverse Shell** mittels Netcat (`nc`), bei der das Opfersystem die Verbindung zum Angreifer initiiert und Firewalls umgeht.

### 3.2. Backdoor in legitime Images
* **Mechanismus:** Angreifer können über ein präpariertes Dockerfile Schadcode (z. B. eine Reverse Shell via Umgebungsvariable `LD_PRELOAD`) in ein scheinbar harmloses Basis-Image (wie Ubuntu) einbauen und auf Plattformen wie Docker Hub bereitstellen.
* **Auswirkung:** Sobald ein Opfer den Container startet, erhält der Angreifer automatisch vollen Shell-Zugriff innerhalb des Containers.

### 3.3. Privilege Escalation durch Volume Mounting
* **Mechanismus:** Wenn ein User der `docker`-Gruppe angehört, besitzt er effektiv Root-Rechte auf dem Host. Wird ein Host-Verzeichnis (z. B. `/tmp/shared`) als Bind-Mount in einen Container eingebunden, in dem standardmäßig Root-Rechte gelten, kann dort eine manipulierte Binärdatei mit gesetztem **SUID-Bit** (`setuid(0)`) abgelegt werden.
* **Auswirkung:** Der Angreifer führt die Datei anschließend auf dem Host aus und erlangt dort ohne Passwort (`sudo`) vollständige Root-Rechte (Auslesen von `/etc/shadow`).

### 3.4. Container Escape durch Docker Socket
* **Mechanismus:** Das Mounten des Unix-Sockets `/var/run/docker.sock` in einen Container gibt diesem die Kontrolle über den Docker-Daemon des Hosts.
* **Auswirkung:** Aus dem Container heraus kann ein neuer, privilegierter Container gestartet werden, der das gesamte Root-Dateisystem (`/`) des Hosts einbindet. Damit bricht der Angreifer komplett aus dem Container aus und kontrolliert den Host.

### 3.5. Kernelspace-Manipulation (`--privileged`)
* **Mechanismus:** Der Start eines Containers mit dem `--privileged`-Flag weist diesem fast alle Linux-Capabilities des Hosts zu, einschließlich `CAP_SYS_MODULE`.
* **Auswirkung:** Ein Angreifer kann aus dem Container heraus eigene Kernel-Module (`.ko`) direkt in den Kernel des Host-Betriebssystems laden (`insmod`) und so uneingeschränkten Zugriff erlangen.

### 3.6. Dangling Volumes
* **Mechanismus:** Das Löschen eines Containers löscht nicht automatisch die mit ihm verknüpften Volumes. Diese verbleiben als ungebundene ("dangling") Volumes auf dem Host.
* **Auswirkung:** Wenn sensible Daten (z. B. Passwörter) darin gespeichert sind, kann ein Angreifer mit Container-Start-Rechten dieses Volume in einen neuen Container einbinden und die Daten stehlen.

## 4. Schützen & Hardening (Gegenmaßnahmen)

### 4.1. Auditierung auf Host-Ebene
* **Maßnahme:** Einsatz des Linux-Audit-Subsystems (`auditd`). Durch das Anlegen von Regeln (`docker.rules`) werden Zugriffe auf kritische Docker-Dateien und -Verzeichnisse (wie `/var/lib/docker`, `daemon.json`, `docker.service`) in Echtzeit überwacht und protokolliert.

### 4.2. Absicherung des Docker Daemons (`daemon.json`)
Die Konfiguration des Daemons sollte restriktiv gehärtet werden:
* `"icc": false`: Verbietet die unverschlüsselte Kommunikation zwischen Containern auf dem Standard-Bridge-Netzwerk, um Sniffing zu verhindern.
* `"live-restore": true`: Hält Container am Laufen, selbst wenn der Docker-Daemon gestoppt oder gewartet wird.
* `"no-new-privileges": true`: Verhindert, dass Prozesse innerhalb des Containers über SUID-Bits zusätzliche Rechte erlangen.
* `"userland-proxy": false`: Deaktiviert den Userland-Proxy zugunsten von performanterem Hairpin NAT über iptables, was die Angriffsfläche reduziert.
* `"default-ulimits"`: Setzt Ressourcen-Obergrenzen für Container, um DoS-Angriffe abzuwehren.

### 4.3. Root im Container vermeiden
* **Maßnahme:** Standardmäßig laufen Container als Root. Im Dockerfile sollte über den Befehl `USER <name>` ein dedizierter, unpriviligierter Systemnutzer (ohne Passwort, Shell und Home-Verzeichnis) definiert werden. Alternativ beim Start das Flag `--user <uid>:<gid>` verwenden.

### 4.4. cgroups zur Ressourcenbegrenzung
* **Maßnahme:** Eindämmung von Schadcode, DoS oder "Fork Bombs" durch strikte Limits:
  * `--cpus 0.5`: Begrenzt die maximale CPU-Nutzung.
  * `--pids-limit 6`: Limitiert die maximale Anzahl paralleler Prozesse im Container (stoppt Fork Bombs).
  * `--memory 256m`: Begrenzt den maximal verfügbaren Arbeitsspeicher.

### 4.5. Least Privilege bei Linux-Capabilities
* **Maßnahme:** Docker nutzt standardmäßig eine reduzierte Whitelist an Capabilities. Best Practice ist es, mit `--cap-drop all` zuerst alle Rechte zu entziehen und nur die absolut notwendigen per `--cap-add <capability>` (z. B. `chown`) gezielt hinzuzufügen.

### 4.6. Systemaufrufe filtern mit Seccomp
* **Maßnahme:** Seccomp filtert Systemaufrufe (`syscalls`) zum Kernel. Durch benutzerdefinierte JSON-Profile können riskante Befehle wie `chmod`, `fchmod` oder `unshare` für den Container blockiert werden, selbst wenn der Prozess darin als Root läuft.

### 4.7. Zugriffskontrolle mit AppArmor
* **Maßnahme:** AppArmor schützt das System über Profile im *Enforced-Modus*. Eigene Profile (`apparmor-profile`) können spezifische Pfade innerhalb des Containers sperren (z. B. `deny /tmp/**` oder `deny /etc/passwd rwklx`), um Datenabfluss trotz Kompromittierung zu verhindern.

### 4.8. User Namespaces aktivieren
* **Maßnahme:** Aktivierung von `--userns-remap=default` in der Daemon-Konfiguration. Dadurch wird die Root-UID 0 des Containers auf eine hohe, unprivilegierte UID auf dem Host (z. B. 231072) gemappt. Bricht ein Angreifer aus, besitzt er auf dem Host keinerlei Rechte.

### 4.9. Verifizierung via Docker Content Trust (DCT)
* **Maßnahme:** Aktivierung über `export DOCKER_CONTENT_TRUST=1`. Docker erzwingt dadurch, dass nur digital signierte und verifizierte Images von vertrauenswürdigen Registries heruntergeladen werden können, was manipulierte "Poisoned Images" blockiert. Auf Docker Hub sollte auf Labels wie *Docker Official Image* oder *Verified Publisher* geachtet werden.

## Wichtigste Key Takeaways
1. **Root-Vermeidung ist die halbe Miete:** Prozesse in Containern sollten standardmäßig niemals als Root laufen. Die Nutzung von unprivilegierten Dockerfile-Usern und die Aktivierung von *User Namespaces* minimieren das Risiko von Privilege Escalations drastisch.
2. **Das Prinzip von Least Privilege konsequent anwenden:** Containern sollten standardmäßig per `ulimits`, `cgroups`, `cap-drop` und restriktiven *Seccomp-/AppArmor-Profilen* alle Berechtigungen und Ressourcen entzogen werden, die sie für ihre primäre Funktion nicht zwingend benötigen.
3. **Gefährliche Flags und Mounts ächten:** Das `--privileged`-Flag sowie das Mounten des Docker-Sockets (`/var/run/docker.sock`) hebeln fast alle Sicherheitsarchitekturen aus und ebnen Angreifern den Weg zum vollständigen Host-Escape. Sie dürfen in produktiven Umgebungen nicht leichtfertig genutzt werden.
4. **Lieferkette absichern (Content Trust):** Blindes Vertrauen in Repositories birgt die Gefahr von integrierten Backdoors. Der Einsatz von *Docker Content Trust* stellt sicher, dass nur verifizierte und unveränderte Images zur Ausführung gelangen.
5. **Kontinuierliches Auditing:** Sicherheitsstatus sind dynamisch. Werkzeuge wie *Docker Security Bench* in Kombination mit aktiver Kernel-Protokollierung (`auditd`) sind essenziell, um Fehlkonfigurationen und Anomalien frühzeitig zu erkennen.
