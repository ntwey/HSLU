## 1. Einleitung & Vorbereitung
Diese Laborübung vermittelt den praktischen Umgang mit einer Public Key Infrastructure (PKI). Der Ablauf erstreckt sich über die Installation einer Zertifizierungsstelle (CA) bis hin zu erweiterten Szenarien wie zertifikatsbasierter Authentifizierung, Code Signing und der Analyse von SSL-Interception.

### Versuchsumgebung
* Windows-Server 2022: Agiert als Active Directory Domain Controller (DC) für die Domäne gXXX.ckteck.com (wobei XXX für die Gruppennummer steht). Hier wird die CA eingerichtet.
* Windows-Client: Ein Windows Server 2022 (simuliert Windows 10/11), der bereits in die Domäne eingebunden ist.
* Linux-Client: Ein Debian 12 (Bookworm) System, das als Apache2-Webserver fungiert.

### Vorbereitungsaufgabe
* Im Windows DNS-Manager wird in der Forward-Lookupzone ein neuer A-Record (www) angelegt, welcher auf die private IPv4-Adresse des Linux-Clients verweist. Dadurch wird der Webserver über den DNS-Namen erreichbar.

## 2. Certification Authority (CA) installieren & konfigurieren
Für die Testumgebung wird eine Two-Tier-PKI-Hierarchie aufgebaut. Die Root-CA wurde bereits vom Laborteam vorkonfiguriert. In der Übung wird eine Issuing CA (auch Subordinate CA genannt) auf dem eigenen Windows-Server installiert.

### Installationsschritte
1. Rollen-Installation: Über den Server Manager wird die Rolle Active Directory Certificate Services (AD CS) hinzugefügt.
2. Benötigte Rollendienste: Certification Authority, Certification Authority Web Enrollment, Certificate Enrollment Web Service, Online Responder.
3. CA-Konfiguration:
   * Setup Typ: Enterprise CA (nutzt das Active Directory zur Zertifikatsverwaltung).
   * CA Typ: Subordinate CA.
   * Private Key: Erstellung eines neuen privaten Schlüssels mit einer Länge von 4096 Bits und dem Algorithmus SHA256.
   * Name: CKTECK CA.
4. Zertifikatskette (Certificate Chain) einbinden: Es wird ein Certificate Signing Request (CSR) erzeugt und über das Webinterface der Root-CA eingereicht. Die ausgestellte Zertifikatskette (certnew.p7b) wird anschließend in der eigenen CA installiert.
5. Active Directory bekannt machen: Das Root-CA-Zertifikat wird mittels des Befehls "certutil -dspublish" im AD publiziert, damit alle Domänenmitglieder ihr automatisch vertrauen.

---

## 3. HTTPS auf Apache2 aktivieren
Um eine unverschlüsselte Webseite auf dem Apache2-Webserver abzusichern, wird manuell ein Webserver-Zertifikat bei der neuen CA beantragt.

### Ablauf auf dem Linux-Client
1. CSR-Konfiguration: Da moderne Browser zwingend Subject Alternative Names (SAN) voraussetzen, wird eine Konfigurationsdatei (request.conf) mit den entsprechenden Attributen erstellt (z. B. CN = www.gXXX.ckteck.com und DNS.1 = www.gXXX.ckteck.com).
2. Schlüsselgenerierung: Mittels OpenSSL wird der private Schlüssel und der CSR generiert. Es wird ein RSA-Schlüssel mit 4096 Bit verwendet. Der Parameter für unverschlüsselte Schlüssel sorgt dafür, dass der Apache-Server ohne Passphrasen-Eingabe starten kann.
3. Zertifikat anfordern: Der Inhalt der CSR-Datei wird im Webinterface der CA unter dem Template "Web Server" eingereicht. Das Base64-codierte Zertifikat wird als "www.cer" auf dem Linux-Server abgelegt.
4. Apache-Konfiguration: In der Datei default-ssl.conf werden die Pfade zum neuen Zertifikat und zum privaten Schlüssel hinterlegt.
5. Module aktivieren & HTTP-Redirect: Das SSL-Modul und die SSL-Site werden aktiviert. In der Standardkonfiguration für Port 80 wird ein permanenter Redirect (Redirect permanent) auf die HTTPS-Adresse eingerichtet.

## 4. Zertifikatsbasierte Authentifizierung & Revocation
In diesem Abschnitt wird der Webserver so konfiguriert, dass nur noch Benutzer mit einem gültigen Client-Zertifikat Zugriff auf die Webseite erhalten.

### Webserver-Konfiguration
Die CA-Zertifikatskette wird ins PEM-Format konvertiert und im Apache hinterlegt. Die Direktive "SSLVerifyClient require" erzwingt die Client-Authentifizierung.

### User Certificate Autoenrollment
Damit Benutzer nicht manuell Zertifikate beantragen müssen, wird das Windows-Feature Autoenrollment genutzt:
1. Template duplizieren: Das vorhandene Template "User" wird dupliziert. In den Sicherheitsberechtigungen erhält die Gruppe "Domain Users" die Rechte Read, Enroll und Autoenroll.
2. Gruppenrichtlinie (GPO): Es wird eine neue GPO erstellt und auf die entsprechende Organisationseinheit (OU) verlinkt. In den Public Key Policies wird die automatische Registrierung und Erneuerung aktiviert. Nach einer erneuten Benutzeranmeldung wird das Zertifikat automatisch im Hintergrund ausgestellt.

### Certificate Revocation (Widerruf)
Um Zertifikate vor Ablauf ihrer Gültigkeit (z. B. beim Austritt eines Mitarbeiters) zu sperren, stehen zwei Mechanismen zur Verfügung:
* Certificate Revocation Lists (CRL): Eine sequentielle Liste gesperrter Zertifikate. Bei großen Infrastrukturen kann das Herunterladen und Prüfen dieser Listen zu Performance-Problemen führen.
* Online Certificate Status Protocol (OCSP): Eine performantere Client-Server-Lösung, bei welcher der Webserver den Status eines spezifischen Zertifikats in Echtzeit beim sogenannten Online Responder anfragt.

### Wichtig: NONCE Extension bei OCSP
In den Eigenschaften der Revocation-Konfiguration des Online Responders muss der NONCE-Support aktiviert werden. Die OCSP Nonce ist ein zufällig generierter Wert, der bei jeder Anfrage mitgesendet wird, um Replay-Angriffe (Wiederholen abgefangener, gültiger OCSP-Antworten durch Angreifer) zu verhindern. Da Apache2 diesen Schutz standardmäßig erwartet, schlägt die Validierung ohne diese Aktivierung fehl.
Nachdem ein Benutzerzertifikat in der CA gesperrt wurde, verweigert der Webserver sofort den Zugriff (Fehlercode im Apache-Log: "certificate revoked").

## 5. Code Signing
Digitale Signaturen schützen Skripte und Binärdateien vor unbefugter Modifikation und weisen deren Integrität und Herkunft nach.

### PowerShell Execution Policies
PowerShell nutzt verschiedene Sicherheitsstufen für die Skriptausführung:
* Restricted: Standard. Es dürfen keine Skripte ausgeführt werden, nur interaktive Befehle.
* AllSigned: Alle Skripte (auch lokale) müssen von einem vertrauenswürdigen Herausgeber signiert sein.
* RemoteSigned: Aus dem Internet herkunftsbasierte Skripte benötigen eine Signatur; lokale Skripte nicht.
* Unrestricted: Führt alle Skripte aus, warnt jedoch bei unsignierten Dateien aus dem Internet.

### Umsetzung im Unternehmen
Per Gruppenrichtlinie wird die restriktive Richtlinie "Allow only signed scripts" (AllSigned) erzwungen.
1. Zertifikat anfordern: Das Template "Code Signing" wird dupliziert und für die Entwickler-Gruppe freigegeben. Der berechtigte Benutzer erhält dadurch sein persönliches Code-Signing-Zertifikat.
2. Trusted Publishers: Damit das System dem Zertifikat vertraut, wird der öffentliche Teil des Entwickler-Zertifikats exportiert und via GPO an alle Clients in den Speicher "Vertrauenswürdige Herausgeber" verteilt.
3. Skript signieren: In der PowerShell wird das Skript mit dem Befehl "Set-AuthenticodeSignature" unter Angabe des Zertifikatspfads signiert. Es wird ein TimeStampServer (z. B. von DigiCert) mitgegeben. Dies sorgt dafür, dass das Skript auch dann noch gültig und ausführbar bleibt, wenn das Zertifikat des Entwicklers nach Ablauf der regulären Gültigkeit erlischt.

Wenn das Skript nachträglich verändert wird (selbst durch das Hinzufügen eines einfachen Kommentars), bricht die Ausführung mit einer Hash-Fehlermeldung ab. Wird das Zertifikat des Mitarbeiters revoziert, sperrt Windows die Ausführung des Skripts sofort.

## 6. SSL Interception (Man-in-the-Middle)
Das "Schloss-Symbol" in der Browser-Adressleiste bedeutet lediglich, dass die Verbindung verschlüsselt ist und das Zertifikat von einer vertrauenswürdigen CA stammt – es garantiert nicht, dass keine Zwischenstation mitliest.

### Funktionsweise mit einem Proxy (z.B. mitmproxy)
Der Linux-Client wird in diesem Szenario als Default-Gateway (Router) konfiguriert. Mittels Firewall-Regeln wird der gesamte HTTP- und HTTPS-Traffic transparent an ein Proxy-Tool umgeleitet.
1. Ohne eigene CA: Ruft der Windows-Client eine HTTPS-Seite auf, bricht der Browser mit einer massiven Sicherheitswarnung ab (Zertifikatsfehler), da das vom Proxy generierte Ad-Hoc-Zertifikat von keiner vertrauenswürdigen Stelle signiert wurde.
2. Mit kompromittierter CA: Besitzt der Angreifer (oder der Firmen-Administrator) jedoch die Rechte, unter der firmeninternen, vertrauenswürdigen PKI eine Subordinate CA für den Proxy auszustellen, passiert Folgendes:
   * Der Proxy fängt den TLS-Handshake ab und bricht die Original-Verbindung auf (SSL Termination).
   * Der Proxy generiert im Bruchteil einer Sekunde ein gefälschtes Zertifikat für die Zielwebseite und signiert es mit seiner legitimen Sub-CA.
   * Da der Client der übergeordneten Firmen-CA blind vertraut, akzeptiert der Browser die Verbindung ohne jegliche Warnung. Das Schloss-Symbol bleibt intakt.
   * Der Proxy baut zum echten Server eine neue SSL-Verbindung auf. Der gesamte Datenverkehr (inklusive Passwörter und Login-Daten) liegt auf dem Proxy im Klartext vor und kann aufgezeichnet oder manipuliert werden.

## 7. Wichtigste Key Takeaways
* Sicherheit von Root-CAs: Eine Root-CA muss im produktiven Umfeld zwingend offline betrieben werden. Wird sie kompromittiert, bricht die Vertrauenswürdigkeit der gesamten nachgelagerten PKI-Hierarchie in sich zusammen.
* Autoenrollment & GPOs: In Windows-Infrastrukturen bieten Gruppenrichtlinien in Kombination mit Zertifikatsvorlagen ein mächtiges Werkzeug, um Tausende von Benutzern und Computern vollautomatisch mit Schlüsseln und Zertifikaten zu versorgen.
* Vorteil von OCSP gegenüber CRL: OCSP-Abfragen sind deutlich ressourcenschonender als klassische Widerrufslisten (CRLs), da sie den Status eines Zertifikats gezielt in Echtzeit validieren, statt große Sperrlisten sequentiell zu durchsuchen.
* Integritätsschutz durch Signaturen: Code Signing schützt Skripte vor unbemerkter Sabotage. Durch die Verwendung eines vertrauenswürdigen Zeitstempel-Servers (Timestamping) bleibt signierter Code auch nach dem regulären Ablaufdatum des Entwicklerzertifikats lauffähig.
* Die Illusion des Schloss-Symbols: Verschlüsselung schützt nicht vor Spionage, wenn der Kommunikationskanal manipuliert wurde. Wer die Kontrolle über die im Betriebssystem hinterlegten Stammzertifikate besitzt (z. B. Arbeitgeber über MDM/GPO), kann mittels SSL Interception den gesamten verschlüsselten Datenverkehr unbemerkt im Klartext mitlesen.
